# Sandbox runtime: ported from bolt.diy

This document is the map between bolt.diy's in-browser execution framework and the
code that now lives in `src/lib/sandbox/`. Nothing is vendored: every module below
is a re-implementation against Solara's own container, store, proxy and UI, because
bolt.diy's versions depend on nanostores, `~/lib/stores/workbench`, Remix SSR
primitives, its own provider router and a persisted chat database, none of which
exist here.

The thing that was actually copied is the *design*, and it is worth stating why it
was copied: the previous loop here was four ad-hoc tools
(`shell`/`read_file`/`write_file`/`list_dir`) wired straight into the chat turn.
It could write a file and run a command. It could not tell whether the file it just
wrote was valid, whether the command it just ran was still the one it was waiting
on, whether its own dev server had crashed, or whether "done" was true. bolt.diy
solves exactly those four problems, and each has a module here.

## What was ported

## The three mechanisms that matter

### 1. A project generation, checked after every await

`createProjectBridge()` captures `projectStore.generation`. Every tool re-checks it
after its awaits, and `callProjectTool` refuses to run against a stale generation.
Consequence: a write that started on project A cannot land in project B when the
user resets the workspace or imports a zip mid-round. bolt.diy does the same with
its workbench `projectGeneration` + `chatId` pair; the chat half is dropped here
because Solara has no server-side chat identity.

### 2. A process registry, not a fire-and-forget spawn

`project_run_command` returns a `processId`, and the registry enforces:

* **installs are gated** — a `run`/`test` command that arrives while an install is
  still in flight either waits (bounded) or is answered with
  `status: 'waiting-for-install'` plus the install's id to poll. This is the single
  most common way an agent reports a phantom failure ("vite: not found") that is
  really "npm install has not finished".
* **`run` is reused** — the same command twice returns `reused: true` instead of
  starting a second dev server on a port that is already bound.
* **secrets of the lifetime are explicit** — a dev server answers `status: 'running'`
  after a 2.5 s grace (long enough to catch a boot crash), everything else answers
  only once its exit code is known.
* **teardown is real** — the registry is killed when the bridge closes, and the
  bridge closes on project reset, zip import and panel teardown.

Exit codes come from a real process (`sh -c`), not from scraping the shared shell,
which is why the gate can trust `exitCode === 0`.

### 3. A completion gate the model cannot talk its way past

`getProgress()` derives, from the call log alone: was a plan recorded, were files
edited, was the app run, did a check pass *after* the last edit and the last
failure, is a preview up. `agent_complete` is rejected with a list of problems and
the exact criteria ids it missed. If the model answers in prose with no tool call
while the gate is unsatisfied, the loop appends `NEXT REQUIRED ACTION: …` and goes
again — up to the user's budget, which is still the only thing that ends a run
early.

That is what makes a 20-requests-a-day free key usable for real work: the sequence
lives in the harness, not in the model's willingness to follow a long prompt.

## Behaviour changes you will notice

* **The path jail now has two roots.** Tools speak `/workspace/...`; the container's
  real workdir is `/home/project`. `path.ts` owns the translation in both
  directions, and shell commands still get the `./` rewrite for a stray
  `/workspace/` prefix (the shell's cwd *is* the project root).
* **The Files tab can now edit and save.** bolt.diy's editor pane, scaled to a
  textarea: saves go through the project store, so the agent sees the change.
* **Zip import resets the runtime.** A new project means new processes; a dev server
  from the imported-over project would keep serving deleted files.
* **The workspace survives a reload.** IndexedDB restore happens before the scaffold,
  so a restart no longer looks like an empty sandbox the model then re-scaffolds.
* **`web_search` / `web_fetch` are real tools now.** They route through
  `/api/search` and the new `/api/fetch-url`, and use the Tavily key from Settings;
  with no key, `web_search` fails with a sentence that says so instead of a 502.
* **The agent loop no longer has a separate `/api/sandbox/turn` payload shape** — it
  was already correct; `provider.ts` now owns it and the loop owns the behaviour.

## What was deliberately not ported

* **Server-side execution / cloud sandboxes.** Solara's stated property is that
  nothing runs on the server. Everything above is in the tab.
* **Git, Netlify/Vercel deploy, Supabase, Expo QR, artifact streaming.** Each is a
  product surface of bolt.diy with no counterpart here; porting them would have
  meant importing bolt.diy's stores rather than its ideas.
* **bolt.diy's MCP *project* bound to `workbenchStore`.** Its store is the source of
  truth for files because it also backs a live editor with unsaved state. Here the
  container filesystem is the truth and `projectStore` is a cache rebuilt by
  `refresh()`, so a file written by `sh` or by an import is visible to the tools
  after a refresh instead of being invisible forever.

## Post-mortem: the run where the gate could never be satisfied

A real session produced five runs in a row whose only output was "no final answer",
one of them ending with `agent_complete` rejected as `Unknown project tool`. The
agent was told by the gate to call a tool the harness refused to execute, so every
run was unwinnable. Six defects, all now covered by tests:

| # | defect | fix |
| --- | --- | --- |
| 1 | `parseToolArguments` validated only `projectToolDefinitions`, so `agent_plan` / `agent_complete` failed as unknown tools while the provider had been told they exist. | The agent tools are declared beside the project tools (`AGENT_TOOL_DEFINITIONS`), and `allToolDefsForProvider()` is the single source for the provider `tools[]`, the validator and the dispatcher. A test asserts advertised ≡ executable. |
| 2 | A turn that called tools and carried reasoning but no prose logged `no final answer; last reasoning: …` — on *every* working round. | That line is only emitted when the model also failed to call a tool. |
| 3 | `agent_complete` accepted the task, then the loop `break`ed before the model could write its summary, leaving an empty chat reply after successful work. | The loop spends one extra request on the summary and treats that prose as the answer. |
| 4 | Gate nudges incremented `stepCount` and could be issued on the final round, so the budget line and the reported cost were both wrong. | Nudges are capped (`MAX_GATE_NUDGES`) and never issued without a round left to act on; `stepCount` counts model requests, `toolRounds` counts tool-calling rounds. |
| 5 | A reasoning model spending 30k reasoning tokens and returning nothing was reported as one generic "turn not completed". | `reasoningOnly()` detects it, one corrective request is sent with an explicit "call a tool or answer" instruction, and a second occurrence stops with advice to *lower* max tokens. |
| 6 | Preview exceptions survive a project reset and were fed to the new project's first round, sending the agent after a file that no longer exists. | `bumpGeneration()` clears the preview-issue queue. |

Two UI consequences of the same session: the Activity tab now opens with a
**"N tools available"** panel listing every callable tool grouped by purpose (derived
from the same definitions, so it cannot drift), and reported preview errors get
**dismiss** and **ask the agent to fix** buttons instead of accumulating forever.

`loop.test.ts` drives the real loop with a scripted provider and asserts on what the
model was *told*, which is the seam all six defects lived in.

## Verifying it

```bash
npm run lint     # tsc --noEmit
npm test         # vitest: path jail, patch/replace semantics, parse-before-save, completion gate
npm run build
npm start        # then open the app, unlock with the password in server.ts, open the Sandbox panel
```

The tests cover the parts where a bug is silent: a jail that lets `..` through, a
line patch that is off by one, a check that ran before the last edit, a completion
gate that accepts a plan as a result. They do not cover the container (needs a
browser), so the first real task you run in the panel is the integration test:
`scaffold a Vite + React counter app, start it, and show me the preview`.

## Streaming, diffs and the thread (v10)

bolt.diy does three things this panel did not, and they are the difference the user noticed:

| Capability | bolt.diy | v9 here | v10 here |
| --- | --- | --- | --- |
| Model output while it is generating | token stream in the assistant bubble | blocking request, whole reply at the end | `/api/sandbox/stream` SSE, coalesced into one live bubble (60 ms flush), `thinking` deltas optional |
| Reviewing a change | per-file diff view | the file's new contents, if you opened it | `change` event with `+/-` counts and a unified patch; badges in the tree, diff toggle in the viewer, changed-files strip in Activity |
| Conversation across reloads | persisted thread | project files persisted, transcript lost | transcript persisted to IndexedDB (400 events) next to the project |

**Streaming contract.** `POST /api/sandbox/stream` validates an https-or-loopback upstream, forces
`stream: true` with `stream_options.include_usage`, and re-emits `reasoning` / `text` / `tool_delta` frames,
then one `done` with the assembled content, tool calls, finish reason and usage. `tool_delta.arguments` is
cumulative per index, so a client never has to concatenate fragments itself. 15 s keepalive comments keep
proxies from closing a reasoning model's long pause. `provider.ts` falls back to the blocking route on any
stream error, so an upstream that ignores `stream` still works.

**Why the stream is reassembled on both sides.** Providers index tool-call fragments and may omit `id` or
`name` on later fragments. The server fills both in and only ever emits a monotonically growing argument
string; the client parses once, at `done`. Anything else means the argument JSON is parsed mid-token.

**Diff contract.** `lineDiff(before, after)` is an LCS over lines, exported for tests. It collapses unchanged
runs to one `… N unchanged line(s)` marker and falls back to remove-all/add-all past 400 000 cells, which is
what keeps a large lockfile from freezing the tab. `change` events carry at most 20 000 characters of patch;
the panel keeps the newest 60 paths.

**One gotcha worth remembering.** Adding a variant to the `AgentEvent` union breaks `ActivityRow`'s
fallthrough return type (TS2339 on `ok`/`tool`/`detail`). Every new event kind needs its own branch *before*
the tool `<details>` return. This bit twice.

## Batching tool calls (v11)

A round trip is the expensive unit, not a tool call. One response can carry several
`tool_calls`, and the loop always supported that — the ceiling was a hard-coded
`slice(0, 8)` and a system prompt that never said "batch", so a model wrote one file per
round and a five-file scaffold cost five requests.

What changed:

| Knob | Where | Meaning |
| --- | --- | --- |
| **requests** | `mode.ts` `ROUNDS_KEY` | how many model requests the task may spend (unchanged, 1–60, default 24) |
| **calls/request** | `mode.ts` `BATCH_KEY` | how many tool calls may come back in ONE response (1–16, default 8) |
| **batch** (checkbox) | `PARALLEL_KEY` | send `parallel_tool_calls` upstream at all; off = one call per round |
| **max tokens** | `TOKENS_KEY` | the size ceiling for a single answer (unchanged, 500–32 000) |

All four are still user-controlled and persisted; none replaced another.

**Wire behaviour.** `provider.ts` sends `parallel_tool_calls: true` unless the toggle is
off. `server.ts` wraps the upstream call in `fetchWithParallelFlag()`, which retries once
without the field when a gateway answers 400/422 naming the parameter (older Azure
deployments and some compat shims do), and reports the downgrade as a `note` event rather
than failing the turn. Measured both paths against a mock that rejects the field on
purpose: the retry succeeds and `parallelDropped` is true.

**Why the ceiling exists at all.** One response carrying 16 writes is 16 approval
prompts, one very long answer that can hit `max_tokens` mid-call (losing the whole
batch), and no interleaved chance to react. Batching is best for independent work —
scaffolding files, several reads — and worst for dependent steps, which the system prompt
now spells out ("only split a step out when it depends on the result of the one before
it: install before run, run before reading an error").

**Token accounting.** Each turn's `usage` is summed into `{prompt, completion, reasoning,
total}` and emitted as a `usage` event after *every* turn, so the panel's counter moves
while the agent works, and once more at the end. `reported: false` means the provider sent
no `usage` at all (some proxies drop it in stream mode) and the panel prints `≥` instead
of a confident number. The chat footer reports **requests and tool calls separately** —
the old footer labelled the request count "tool calls", which made a correctly batched
turn look wrong.
